---
name: wl-workspace
description: Create or update a wl workspace. Use when the user wants to save their current project setup, create a workspace, capture this session for later, or says anything about wl/workspace/launch configuration; also when they want to refresh workspace instructions, add or fix skills, fix paths, or sync the workspace with how the project has evolved ("update workspace", "refresh workspace", "sync workspace"). Also trigger when the user has been working in a multi-repo or multi-folder setup and wants to persist it.
---

Create a new wl workspace, or detect drift in an existing one, and propose reviewable changes. Be opinionated — propose your best guess, then let the user confirm or adjust. Never silently write workspace files: propose, wait for explicit approval, then apply.

## Rules for every workspace

- Workspaces live under `WL_WORKSPACES_ROOT` when set, otherwise `~/.wl-workspaces`. Each workspace is one folder: `<root>/<slug>/`.
- `workspace.json` must contain `"schemaVersion": 2`. Other fields: `name`, `primaryRepo`, `additionalDirs`, and optional `copilotArgs` (Copilot CLI arguments added to every launch, e.g. `["--yolo"]`). Sessions resume by default; there is no field for it.
- Relative paths in `workspace.json` resolve from the workspace folder. Prefer `~/` and `$VAR` paths (see **Portable paths**).
- `<workspace>/AGENTS.md` holds the workspace instructions. wl adds the workspace folder to `COPILOT_CUSTOM_INSTRUCTIONS_DIRS`, so Copilot loads it. `.shared/AGENTS.md` (if present) applies to every workspace.
- Workspace skills live in `<workspace>/.copilot/skills/<name>/SKILL.md` and are exposed via `--plugin-dir`. `.copilot/plugin.json` is generated by wl — never edit it.
- Commands: `wl launch [name]`, `wl which [name]` (shows resolved paths and the exact Copilot command without changing anything), `wl create [name]`, `wl clone <url>`. Path variables live in `~/.wl-workspaces/.paths.json`; `wl launch` prompts for undefined ones.

## Choose the mode

1. Inspect the workspaces root folder. Look for a workspace whose folder is attached to this session (additional dirs) or whose `primaryRepo` is the current repo.
2. If one exists, use **Update**. If none exists, use **Create**. Never overwrite an existing workspace from Create — even if `wl which` reports a load error, switch to Update and propose the fix.
3. Only ask the user if this doesn't resolve to a single answer.

## Create

### 1. Gather context

First, assess session warmth. If you were invoked as the first/early turn of a fresh session with no real work done yet (no files explored, no commands run, no prior substantive turns), treat it as a **cold session**. Otherwise it's **warm**.

**Cold session — ask before proposing.** Silent analysis would produce a shallow proposal. Use the question tool to ask 3–5 concrete questions with sensible defaults, covering:

- Single repo or multi-repo — and if multi, the other paths
- Typical commands run here (build, test, lint, deploy)
- External docs, specs, or OneDrive/shared folders worth attaching
- Workspace-level quirks to encode (auth setup, env vars, team conventions)
- Workflows worth capturing as skills — or "none" (a valid answer; see **Skill threshold**)

Don't ask open-ended "tell me about your project" questions.

**Warm session — gather silently:**

- **Primary repo**: the current working directory (check for `.git`)
- **Additional dirs**: referenced paths, imports from other repos, external docs/specs mentioned, `--add-dir` flags used, OneDrive/shared folders discussed
- **Project type**: language, framework, build system (`package.json`, `*.csproj`, `Cargo.toml`, `go.mod`, …)
- **Conventions**: coding style, architecture patterns, testing approach observed in the session
- **Workflows**: what the user has been doing — debugging, reviewing, testing, deploying. Candidates for skills.
- **Existing docs**: read the repo's `AGENTS.md`, `.github/copilot-instructions.md`, `.github/instructions/*`, and repo skills in the primary repo and additional dirs. You need to know what they cover so you don't repeat it.
- **Runtime**: verify `copilot --version`.

### 2. Pre-proposal checklist

Walk through these filters before proposing. They prevent the two common failures: duplicating repo instructions and inventing thin wrapper skills.

1. **Duplication-diff.** For each bullet you plan to put in the workspace `AGENTS.md`, name the specific file or section that does *not* already cover it. If you can't, drop the bullet. Workspace instructions capture what repo instructions don't — cross-repo relationships, additional-dir setup, environment quirks.
2. **Portable paths.** Apply **Portable paths** to `primaryRepo`, every `additionalDirs` entry, and any path you mention in `AGENTS.md` prose.
3. **Skill threshold.** Apply **Skill threshold** to every proposed skill. "None" is often the right answer.
4. **Shape.**
   - **Minimal workspace** — the repo instructions are thorough, there are no additional dirs or cross-repo concerns, and no skill clears the threshold. Propose it in one shot: config, a one-line `AGENTS.md` pointing at the repo instructions, no skills. Don't scaffold full content and whittle it down over several rounds.
   - **Full workspace** — additional dirs, cross-repo concerns, or real workspace-level context.

### 3. Propose

Pick a slug that names the project, not the task: lowercase with hyphens, short and recognizable (`backend-api`, `data-pipeline`). For multi-repo work, name the overall system. Set `copilotArgs` to `["--yolo"]` if the current session already runs with all permissions (`--yolo` / `--allow-all`); otherwise leave it out. Include only reviewed Copilot CLI flags.

**Minimal template:**

```
Proposed workspace: <slug>  (minimal)

  Name:         <display name>
  Primary repo: <path>
  Additional:   none
  Copilot args: none / ["--yolo"] / <other reviewed flags>

  AGENTS.md: one line pointing to the repo's own instructions
  Skills to create: none

Reasoning: <one sentence on why nothing else is warranted>

Good to create it? (Say "no Copilot args" or name the exact flags to change them.)
```

**Full template:**

```
Proposed workspace: <slug>

  Name:         <display name>
  Primary repo: <path>
  Additional:   <path1>, <path2>
  Copilot args: none / ["--yolo"] / <other reviewed flags>

  AGENTS.md will cover:
    - <bullet — and the repo instruction file that does NOT cover it>

  Skills to create:
    - wl-<skill> — <what it does, and why it clears the threshold>
    (omit this section if nothing cleared the threshold)

Does this look right? Any changes before I create it?
```

**HARD STOP — end your turn here.** Output the proposal as your final message and call no tools in the same turn. Don't write `workspace.json`, `AGENTS.md`, or skills until the user approves in a new turn. This applies in autopilot too: workspace files are durable user config. "Yes" / "looks good" / "go ahead" is approval; anything else is feedback — re-propose instead of applying edits and creating in one shot.

### 4. Create (the turn after approval)

1. Write `<root>/<slug>/workspace.json`:
   ```json
   {
     "schemaVersion": 2,
     "name": "<display name>",
     "primaryRepo": "<repo path>",
     "additionalDirs": ["<dir1>"],
     "copilotArgs": ["--yolo"]
   }
   ```
   Omit `copilotArgs` when empty. If you introduced a new `$VAR`, add it to `~/.wl-workspaces/.paths.json` for this PC.
2. Write `<root>/<slug>/AGENTS.md` — the most important file. Cover what applies: system overview (what each repo/folder is and how they relate), architecture, conventions, debugging (logs, common failures), workflow (build/test/deploy commands and order). Only what the repo instructions don't already say. Be specific — real paths, real commands. 10–30 lines is the sweet spot. Never write placeholders like "(describe your project)".
3. Create only the approved skills, using **Skill format**. If the proposal said "none", create none.
4. Run `wl which <slug>`, show its output, and tell the user to run `wl launch <slug>`.

## Update

### 1. Read the workspace

Read `workspace.json`, `AGENTS.md`, every `.copilot/skills/*/SKILL.md`, and any other workspace files. Run `wl which <slug>` for resolved paths and warnings. If it reports a load error, show it and propose the fix.

### 2. Detect drift

Don't rely only on conversation history — a fresh session may have none. Investigate:

- **Repo instructions**: read the primary repo's `AGENTS.md` / `.github/instructions/*` and flag workspace `AGENTS.md` content that duplicates them.
- **Recent changes**: `git log --oneline -20` in the primary repo for renamed files, new build steps, moved directories.
- **File tree**: list key directories for new, removed, or restructured folders the workspace `AGENTS.md` doesn't reflect.
- **Skills**: verify every command, path, and step each skill references still exists.

Classify what you find:

- **Additions** — a repo or folder used but not in `workspace.json`; a recurring instruction pattern not documented; a repeated workflow that clears the skill threshold; an external folder referenced but not attached.
- **Removals** — dirs never touched; skills that no longer match workflows or don't clear the threshold; obsolete workspace files.
- **Modifications** —
  - instructions referencing renamed files, removed patterns, or old decisions
  - changed paths, commands, or step order (in `AGENTS.md` or skills)
  - `copilotArgs` that no longer match how the workspace is used
  - fields wl doesn't use (e.g. `yolo`, `resume`) — propose removing them; `"yolo": true` becomes `"copilotArgs": ["--yolo"]`
  - skills without the `wl-` prefix, or missing `name`/`description` frontmatter
  - non-portable paths (see **Portable paths**), including redundant `$VAR`s that map to the same root as an existing one, and subdirectories of `primaryRepo` listed as additional dirs
- Missing `allowed-tools` is not drift. Never add or broaden approvals automatically.
- If Copilot is unavailable, check `copilot --version` and suggest installing it or fixing PATH.

### 3. Propose

Show real content for `AGENTS.md` changes — "updated section X" isn't enough to approve.

```
## Workspace update proposal: <slug>

### Added
- <item> — <why>

### Removed
- <item> — <why>

### Updated
- AGENTS.md: <section>
  - Before: "<quoted old text>"
  - After: "<quoted new text>"
- skills/wl-<name>: <what changed and why>

### No changes needed
- <files you checked and left alone>

Apply these changes?
```

If nothing needs updating, say so and stop. Otherwise **HARD STOP** as in Create.

### 4. Apply (the turn after approval)

1. Apply only the approved changes.
2. Edit `AGENTS.md` sections in place — don't rewrite from scratch. Preserve the user's structure and voice.
3. In skills, change only the commands, paths, and steps that changed; keep existing structure and `allowed-tools`.
4. Run `wl which <slug>` and summarize: N additions, N removals, N updates.

## Portable paths

Apply in order to every path:

1. **Under the user's home → `~/`.** `C:\Users\me\docs\x` or `/Users/me/docs/x` becomes `~/docs/x`.
2. **Reuse existing variables.** Read `~/.wl-workspaces/.paths.json` first. If a variable already maps to the right root (e.g. `REPOS = D:\repos`), use `$REPOS/...`. Don't invent a second name for the same root.
3. **Other absolute paths → `$VAR`.** Drive-absolute (`D:\repos\x`) or root-absolute (`/opt/x`, `/mnt/x`) paths become `$NAME/...`, with `NAME` added to `.paths.json`. Don't invent `$HOME` — use `~/`.
4. **Skip subdirectories of `primaryRepo`** as additional dirs — they're already attached.
5. **In `AGENTS.md` prose**, use `~/`, `$VAR`, or paths relative to the repo root — never drive-absolute paths.

## Skill threshold

Propose a workspace skill only if at least one holds:

- it takes **3+ steps**
- it encodes **non-obvious knowledge** not in `AGENTS.md` or repo skills
- it's a **multi-command workflow**, not one command with flags

One-line command wrappers add noise. When nothing clears the bar, "none" is the right answer.

## Skill format

```markdown
---
name: wl-<skill-name>
description: <what this skill does and when to use it>
---

<concrete instructions: actual commands, paths, and steps>
```

- Always use the `wl-` prefix for workspace skills.
- `name` and `description` are required. `allowed-tools` is optional permission pre-approval (Copilot tool names, e.g. `shell`); omit it unless the user explicitly asks after reviewing the skill.
- Users can invoke a skill by name (`/wl-review`) or let Copilot pick it from the description.
